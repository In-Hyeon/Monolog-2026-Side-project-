# monolog ERD 엔티티 정리

`Monolog_s2.sql` (1단계 + 2단계 통합 ERD) 기준으로, 13개 엔티티를 4개 도메인으로 묶어 정리한 문서입니다.

## 도메인 개요

```
Account (User, NotificationSetting)
   ↑ 모든 도메인이 User를 참조
Relationship (Friend, Groups, GroupMember)
   ↑ Groups를 아래 두 도메인이 참조
Diary (Diary, DailyPrompt, DiaryGroupShare)
Group Communication (GroupQuestion, GroupAnswer, QuestionBookmark, AnswerBookmark, ChatMessage)
```

`Diary`와 `Group Communication`은 서로 FK로 얽히지 않고 둘 다 `Groups`만 참조하는 형제 관계다. 그룹은 일기 공유용과 QnA/채팅용을 겸하는 단일 엔티티로 설계했다(기획서 38, 204행).

---

## 1. Account — 계정/설정

### User

**존재 이유**: 서비스의 모든 도메인이 참조하는 루트 엔티티. Firebase Authentication으로 처리한 로그인(Google/Kakao)을 내부 DB 레코드와 연결하는 역할을 한다. 로그인 자격 증명 자체(비밀번호 등)는 Firebase가 관리하고, 이 테이블은 프로필/식별 정보만 가진다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | DB 내부 식별자 |
| `firebaseUid` | VARCHAR(128) | - | ✅ | ❌ | 없음 | Firebase Auth가 발급한 UID, 로그인 세션 매칭용 |
| `email` | VARCHAR(255) | - | ✅ | ❌ | 없음 | 로그인 계정 이메일(Google/Kakao) |
| `name` | VARCHAR(50) | - | ❌ | ❌ | 없음 | 화면에 표시되는 닉네임 |
| `profileImage` | VARCHAR(2048) | - | ❌ | ✅ | `NULL` | 프로필 사진 URL, 없으면 기본 아바타 |
| `createdAt` | TIMESTAMP | - | ❌ | ❌ | `now()` | 가입 시각 |
| `updatedAt` | TIMESTAMP | - | ❌ | ❌ | `now()` | 프로필 정보 최종 수정 시각 |

### NotificationSetting

**존재 이유**: 알림을 카테고리별로 on/off할 수 있어야 한다는 요구사항(기획서 87-89행)을 위한 테이블. `User`에 boolean 컬럼을 여러 개 두는 대신, 카테고리가 늘어나도 스키마 변경 없이 행만 추가하면 되도록 세로형(long format)으로 설계했다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 설정 레코드 식별자 |
| `userId` | UUID | FK→User.id | - | ❌ | 없음 | 설정 대상 사용자 |
| `category` | VARCHAR(20) | - | - | ❌ | 없음 | 값: `personalPrompt` / `groupQna` / `groupChat` |
| `enabled` | BOOLEAN | - | - | ❌ | `true` | 해당 카테고리 알림 수신 여부 |
| 복합 제약 | - | - | ✅ `(userId, category)` | - | - | 사용자당 카테고리별 설정 1건 |

## 2. Relationship — 관계 관리

### Friend

**존재 이유**: User↔User 자기참조 관계로 친구 요청/수락 흐름을 표현. 요청자와 수신자를 구분해야 하므로 단순 M:N이 아니라 `requesterId`/`addresseeId`로 방향성을 가진 junction table로 설계했다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 친구 관계 식별자 |
| `requesterId` | UUID | FK→User.id | - | ❌ | 없음 | 요청 보낸 사용자 |
| `addresseeId` | UUID | FK→User.id | - | ❌ | 없음 | 요청 받은 사용자 |
| `status` | VARCHAR(10) | - | - | ❌ | `'pending'` | 값: `pending`(대기) / `accepted`(수락). `CHECK("requesterId" <> "addresseeId")`로 자기 자신에게 요청하는 것을 DB 레벨에서 차단 |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 요청 생성 시각 |
| 복합 제약 | - | - | ✅ `(requesterId, addresseeId)` | - | - | 동일 방향 중복 요청 방지 |

### Groups

**존재 이유**: 일기 공유 대상 그룹과 QnA/채팅 그룹을 하나의 엔티티로 통합한 테이블(기획서 38, 204행 — 두 기능이 별도 도메인으로 보이지만 "같은 그룹"을 공유하는 구조가 기획 의도). 초대코드 기반 참여를 지원하며, 코드는 24시간 후 만료된다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 그룹 식별자 |
| `name` | VARCHAR(100) | - | ❌ | ❌ | 없음 | 그룹 이름 |
| `ownerId` | UUID | FK→User.id | - | ❌ | 없음 | 그룹장 |
| `inviteCode` | VARCHAR(20) | - | ✅ | ❌ | 없음(앱에서 랜덤 생성) | 참여용 초대 코드, 재발급 시 값 갱신 |
| `codeIssuedAt` | TIMESTAMP | - | - | ❌ | `now()` | 현재 코드 발급 시각 |
| `codeExpiresAt` | TIMESTAMP | - | - | ❌ | 없음(앱에서 발급시각+24h 계산해 삽입) | 이 시각 이후 코드 자동 무효화(조회 시점 검증) |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 그룹 생성 시각 |

### GroupMember

**존재 이유**: User↔Groups의 M:N 관계를 해소하는 junction table. 단순 소속 여부뿐 아니라 그룹장/일반 멤버 권한(role)까지 함께 관리한다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 매핑 레코드 식별자 |
| `groupId` | UUID | FK→Groups.id | - | ❌ | 없음 | 소속 그룹 |
| `userId` | UUID | FK→User.id | - | ❌ | 없음 | 멤버 아이디 |
| `role` | VARCHAR(10) | - | - | ❌ | `'member'` | 값: `owner`(그룹장) / `member`(일반 멤버) |
| `joinedAt` | TIMESTAMP | - | - | ❌ | `now()` | 가입 시각 |
| 복합 제약 | - | - | ✅ `(groupId, userId)` | - | - | 동일 그룹 중복 가입 방지 |

## 3. Diary — 일기 & 공유

### Diary

**존재 이유**: 서비스의 메인 기능. `entryType` 컬럼으로 원라인(quick)과 정식 작성(full)을 한 테이블에서 구분해, "이어쓰기"(원라인 → 정식 작성으로 확장) 기능을 별도 테이블 마이그레이션 없이 지원한다. `content`는 별도 테이블로 쪼개지 않았는데, PostgreSQL의 TOAST가 큰 TEXT 값을 자동으로 행 밖에 저장해주기 때문에 수동 분리는 실익이 없다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 일기 식별자 |
| `authorId` | UUID | FK→User.id | - | ❌ | 없음 | 이 일기를 작성한 작성자 |
| `entryType` | VARCHAR(10) | - | - | ❌ | `'quick'` | 값: `quick`(원라인) / `full`(정식 작성) |
| `content` | TEXT | - | - | ❌ | 없음 | 일기 본문 |
| `emoji` | VARCHAR(16) | - | - | ✅ | `NULL` | 원라인 모드 이모지, full 작성 시 비워도 됨 |
| `privacyScope` | VARCHAR(10) | - | - | ❌ | `'private'` | 값: `private`(나만보기) / `public`(전체공유) / `group`(그룹선택) |
| `promptId` | UUID | FK→DailyPrompt.id | - | ✅ | `NULL` | 질문 프롬프트로 작성 시 연결, 자유 작성이면 NULL |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 최초 작성 시각 |
| `updatedAt` | TIMESTAMP | - | - | ❌ | `now()` | "이어쓰기"로 수정 시 갱신 시각 |

### DailyPrompt

**존재 이유**: 개인 AI 질문 프롬프트 기능(기획서 28-29행)의 MVP 버전. 실제 AI 생성 대신 정적 질문 뱅크에서 매일 하나씩 발송하는 방식으로 우선 구현한다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 질문 식별자 |
| `questionText` | VARCHAR(255) | - | - | ❌ | 없음 | 매일 발송되는 질문 문구 |
| `rotationKey` | VARCHAR(20) | - | - | ✅ | `NULL` | 요일/계절 로테이션 태그(예: mon, summer) |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 질문 뱅크 등록 시각 |

### DiaryGroupShare

**존재 이유**: `Diary.privacyScope = 'group'`일 때, 어떤 그룹들에 선택적으로 공유했는지를 표현하는 Diary↔Groups M:N junction table. 세분화된 공유 권한 설정(기획서 42-47행)을 지원한다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 매핑 레코드 식별자 |
| `diaryId` | UUID | FK→Diary.id | - | ❌ | 없음 | 공유되는 일기 |
| `groupId` | UUID | FK→Groups.id | - | ❌ | 없음 | 공유 대상 그룹 |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 공유 설정 시각 |
| 복합 제약 | - | - | ✅ `(diaryId, groupId)` | - | - | 동일 일기-그룹 중복 공유 방지 |

## 4. Group Communication — 그룹 QnA & 채팅 (2단계)

### GroupQuestion

**존재 이유**: 그룹 멤버가 자율적으로 등록하는 스토리형 질문(기획서 49-62행). `DailyPrompt`는 고정 뱅크에서 나오는 정적 텍스트지만, 이건 멤버가 직접 작성하는 자유 텍스트라 별도 엔티티로 분리했다. 48시간 소프트 삭제 정책을 위해 `expiresAt`/`isDeleted`를 둔다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 질문 식별자 |
| `groupId` | UUID | FK→Groups.id | - | ❌ | 없음 | 어느 그룹의 QnA인지 |
| `authorId` | UUID | FK→User.id | - | ❌ | 없음 | 질문을 등록한 멤버 |
| `questionText` | TEXT | - | - | ❌ | 없음 | 질문 본문. 멤버가 자율 작성하는 텍스트라 `DailyPrompt.questionText`(고정 뱅크)와 달리 길이 제한 없이 TEXT |
| `photoUrl` | VARCHAR(2048) | - | - | ✅ | `NULL` | 질문에 첨부한 사진 URL |
| `expiresAt` | TIMESTAMP | - | - | ❌ | 없음(앱에서 생성시각+48h 계산해 삽입) | 이 시각 이후 소프트 삭제 대상 |
| `isDeleted` | BOOLEAN | - | - | ❌ | `false` | 48시간 경과 후 소프트 삭제 플래그 |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 질문 등록 시각 |

### GroupAnswer

**존재 이유**: `GroupQuestion`에 대한 답변. 부모 질문이 소프트 삭제되면 답변도 조회 시 자연스럽게 함께 가려지므로, 답변 자체에는 별도 삭제 플래그를 두지 않았다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 답변 식별자 |
| `questionId` | UUID | FK→GroupQuestion.id | - | ❌ | 없음 | 어느 질문에 대한 답변인지 |
| `authorId` | UUID | FK→User.id | - | ❌ | 없음 | 답변자가 누구인지 |
| `answerText` | TEXT | - | - | ❌ | 없음 | 답변한 내용 본문 |
| `photoUrl` | VARCHAR(2048) | - | - | ✅ | `NULL` | 답변에 첨부한 사진 URL |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 답변 작성 시각 |

### QuestionBookmark / AnswerBookmark

**존재 이유**: 질문/답변을 사용자별로 개별 저장하는 기능. 하나의 테이블에서 questionId/answerId 중 하나만 채우는 폴리모픽 설계 대신, 각 대상별로 명확한 FK를 갖는 두 개의 테이블로 분리했다 — FK가 정확히 하나의 대상만 가리켜야 참조 무결성이 제대로 걸리기 때문이다.

**QuestionBookmark**

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 저장 레코드 식별자 |
| `userId` | UUID | FK→User.id | - | ❌ | 없음 | 저장한 사용자 |
| `questionId` | UUID | FK→GroupQuestion.id | - | ❌ | 없음 | 저장 대상 질문 |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 저장한 시각 |
| 복합 제약 | - | - | ✅ `(userId, questionId)` | - | - | 같은 질문 중복 저장 방지 |

**AnswerBookmark**

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 저장 레코드 식별자 |
| `userId` | UUID | FK→User.id | - | ❌ | 없음 | 저장한 사용자 |
| `answerId` | UUID | FK→GroupAnswer.id | - | ❌ | 없음 | 저장 대상자의 답변 |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 저장한 시각 |
| 복합 제약 | - | - | ✅ `(userId, answerId)` | - | - | 같은 답변 중복 저장 방지 |

### ChatMessage

**존재 이유**: 그룹 실시간 채팅(1:1 제외, 기획서 49-62행). 별도 `ChatRoom` 테이블 없이 `Groups`가 채팅방 역할을 겸한다. 메시지 본문은 항상 목록 조회 시 함께 필요하므로(Diary의 캘린더 뷰처럼 content 없이 조회하는 케이스가 없음), 별도 content 테이블로 분리하지 않았다.

| 필드 | 타입 | PK/FK | Unique | Nullable | 기본값 | 설명 |
|---|---|---|---|---|---|---|
| `id` | UUID | PK | - | ❌ | `gen_random_uuid()` | 메시지 식별자 |
| `groupId` | UUID | FK→Groups.id | - | ❌ | 없음 | 어느 그룹 채팅방인지(별도 ChatRoom 테이블 없이 Groups가 채팅방 역할을 겸함) |
| `authorId` | UUID | FK→User.id | - | ❌ | 없음 | 발신자 |
| `content` | TEXT | - | - | ❌ | 없음 | 메시지 본문 |
| `createdAt` | TIMESTAMP | - | - | ❌ | `now()` | 전송 시각 |
