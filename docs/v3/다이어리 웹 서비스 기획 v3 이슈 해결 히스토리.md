## **`1. v2 → v3 통합 시점 이슈`**

`다이어리 기획 v2 검토 이슈.md`에서 정리했던 6개 이슈. v2에 신규 반영한 2가지 기능(원라인 모드/AI 질문 프롬프트, 그룹 위클리 체크인)이 기존 기획과 충돌하거나 정의가 비어있던 지점들.

| # | 문제 | 해결 |
|---|---|---|
| 1 | AI 커버 일러스트 생성 조건("사진 없이 글만 쓴 날")이 원라인 모드에도 그대로 해당되어, 가장 저부담 기능이 가장 비용 큰 이미지 생성 API를 매일 트리거할 위험 | 자동 생성 → **사용자가 "생성" 버튼을 눌러야 실행되는 온디맨드 방식**으로 변경. 작성 중 이탈 시 임시저장 확인 팝업 추가 |
| 2 | 그룹 위클리 체크인 응답은 그룹 전체 공개가 전제인데, 일기의 "나만보기" 설정과의 관계가 미정의 | 그룹 QnA/채팅을 프라이버시 체계와 **분리된 별도 카테고리**로 정의 — 항상 그룹 내 공개, 개별 비공개 전환 불가 |
| 3 | "스트릭(연속 기록일수)"이라는 표현만 있고 실제 기능으로는 어디에도 정의되지 않음 | **비압박형 "기록 일수 카운터"**로 확정. 페널티·경고·랭킹/배지 등 경쟁·손실 유발 요소는 배제(서비스 톤 유지 우선) |
| 4 | 셋로그 벤치마킹 취지 중 "낮은 진입장벽"은 반영했지만, 또 다른 축인 "AI 시대의 편집 없는 진짜"는 AI 자동생성 기능들과 철학적으로 충돌 | 기존 방향(자동 생성) 유지로 결정 — AI 감성 케어가 서비스 정체성이므로 문제 없다고 판단 |
| 5 | AI 질문 프롬프트(1단계 MVP)는 매일 알림이 필요한데, 알림 스케줄링 인프라가 로드맵상 그룹 체크인(2단계) 맥락으로만 읽혀 MVP 공수 산정에서 누락될 위험 | 로드맵 1단계 설명에 알림 스케줄링 인프라를 명시적으로 포함 |
| 6 | 원라인으로 시작해 AI가 제목/이미지를 생성한 뒤 "이어쓰기"로 내용이 크게 바뀌면, 기존 AI 생성물을 재처리할지 정책이 없음 | 이슈 1의 온디맨드 방식 도입으로 자연히 해소 — "생성" 버튼을 다시 누르면 새 이미지가 생성되므로 별도 재처리 정책 불필요 |
| 7 | (사용자 주도 재설계) 그룹 위클리 체크인의 "시스템 주도 정기 발행 + 동시공개잠금" 구조가 실제 원하는 방향과 다름 | **전면 재설계**: 멤버가 원할 때 자율적으로 질문 등록 + 실시간 답변 + 48시간 후 소프트 삭제(인스타 스토리/셋로그 스타일)로 변경. 그룹 채팅 기능 신규 추가 |

## **`2. v3 완성 후 반복 검토에서 발견된 이슈`**

v3 최초 작성 후, 기술 스택 추천 및 반복 재검토 과정에서 추가로 드러난 이슈들.

### 2-1. 그룹 생성/관리 기능 자체가 정의되지 않음

- **문제**: 프라이버시 설정, 그룹 QnA/채팅 모두 "그룹"을 전제로 서술하지만, 그룹을 어떻게 만들고 초대하고 관리하는지에 대한 CORE FEATURE가 없었음. 또한 일기 공유용 그룹과 QnA/채팅용 그룹이 같은 엔티티인지도 불명확.
- **해결**: CORE FEATURES에 **"친구 및 그룹 관리"** 섹션 신설. 그룹은 일기 공유와 QnA/채팅이 **동일한 단일 엔티티**를 공유하도록 명확화. 그룹장/멤버 권한 정의.

### 2-2. 알림 피로도가 "SNS 피로감 탈피" 브랜드 톤과 상충

- **문제**: 개인 AI 질문 프롬프트(매일) + 그룹 QnA 등록 시마다 + 그룹 채팅 메시지마다, 알림이 3중으로 쌓이는데 알림 제어 수단이 전혀 없었음.
- **해결**: CORE FEATURES에 **"알림 설정"** 섹션 신설 — 카테고리별(개인 질문/그룹 QnA/그룹 채팅) 개별 on/off + 전체 일괄 끄기. 로드맵 1단계부터 포함.

### 2-3. 친구/그룹 추가 방식 미정 — 카카오톡식 vs 코드식

- **문제**: 친구·그룹을 어떤 방식으로 추가할지(연락처 검색 기반 vs 초대 코드 기반) 결정되지 않음.
- **해결**: **초대 코드/링크 기반**으로 통일. 카카오톡식 연락처 검색·매칭 인프라는 사이드 프로젝트 범위에 비해 구축 부담이 크고, 그룹 특성상 이미 아는 사람들끼리 만드는 폐쇄형이라 코드 공유만으로 충분하다고 판단.

### 2-4. 임의로 추가한 "그룹장 허가" 게이트 규칙의 정의 미비 (🔴 실질적 문제)

- **문제**: "그룹장이 허용해야 멤버가 그룹에 일기를 공유할 수 있다"는 규칙을 문서화 과정에서 임의로 추가했으나, 다음이 전혀 정의되지 않았음: 범위(그룹 단위 vs 멤버별 개별 승인), 기본값(신규 그룹의 초기 상태), 소급 처리(권한 철회 시 기존 공유물 처리), UX(권한 없을 때의 화면 동작). 게다가 TECHNICAL POINT의 그룹 엔티티 설계에는 이를 저장할 필드조차 없어 CORE FEATURES와 기술 설계가 불일치.
- **해결**: **B안 채택 — 규칙 삭제.** 그룹 멤버는 누구나 자신이 속한 그룹에 자유롭게 일기 공유 가능하도록 단순화. 별도 엔티티 필드·승인 UI가 필요 없어져 기존 그룹 엔티티 설계와 자동으로 정합됨. 프로젝트 전반의 "구현 부담 최소화" 기조와도 일관성 확보.

### 2-5. 초대 코드 참여·만료 정책 구체화

- **문제**: 그룹 참여 시 승인 절차가 있는지, 초대 코드가 영구적인지 여부가 불명확.
- **해결**: 코드를 입력하면 **승인 절차 없이 누구나 즉시 그룹 참여** 가능하도록 확정. 코드에 **유효시간(TTL, 예: 24시간)**을 부여해 시간 경과 시 자동 파기 — 이후 그룹장이 재발급해야 참여 가능.

### 2-6. 로드맵 표현 혼동 및 기술 포인트 누락 (사소한 정리)

- **문제**: ROADMAP의 "3단계 공유 권한(나만보기/전체/그룹)"이라는 표현이 원래 "3종류"라는 뜻인데, CORE FEATURES 섹션 번호(3번=프라이버시 설정)와 우연히 일치해 혼동 소지 있었음. 또한 TECHNICAL POINT의 FE 항목에 그룹 생성 폼·초대 코드 발급/재발급 화면 UI에 대한 언급이 빠져 있었음.
- **해결**: "3단계" → **"3종"**으로 표현 수정. FE 항목에 **"그룹/친구 관리 화면 UI"** 추가.

### 2-7. 오픈 초대 코드와 "세분화된 프라이버시" 컨셉의 긴장 (🟡)

- **문제**: 재사용 가능한 단일 코드로 승인 없이 누구나 즉시 입장 가능한 구조라, 코드가 유출되면 그룹장이 사후 강제 탈퇴시키기 전까지 프라이버시 그룹의 콘텐츠가 노출될 수 있음. "세분화된 프라이버시"가 핵심 셀링포인트인 서비스에서 그룹 입장 자체는 무방비로 열어두는 셈이라는 지적.
- **선택지**: a) 현행 유지(단일 코드+TTL만) b) 코드 사용 횟수 제한 c) 그룹장에게 신규 입장 알림
- **해결**: **a안 채택** — 그룹 특성상 소규모 지인 모임이라 리스크가 낮다고 판단, 별도 수정 없이 현행 설계(단일 재사용 코드 + TTL) 유지.

### 2-8. 일기 vs 그룹 QnA 프라이버시 분리 의도 검증

- **확인 요청**: "일기는 공개 범위를 사용자가 설정할 수 있지만, QnA 답변은 항상 그룹 멤버만 볼 수 있어야 한다"는 의도가 문서에 정확히 반영됐는지 검증 요청.
- **검토 결과**: 의도대로 정확히 반영되어 있음을 확인 — 일기는 프라이버시 설정(3번) 3종 중 사용자가 매번 선택, 그룹 QnA/채팅(4번)은 "프라이버시 설정과 무관하게 항상 그룹 내 전원 공개"로 고정. 두 체계가 문서 곳곳에서 명시적으로 교차 참조되며 분리되어 있고, 기술 설계상으로도 그룹 QnA 엔티티가 "프라이버시 체계와 분리된 별도 접근 로직"으로 별도 명시됨.

## **`요약`**

총 16개 이슈(v2→v3 통합 7개 + v3 반복 검토 9개, 검증 1건 포함)가 발견·해결되었으며, v3는 현재 알려진 충돌·미정의 지점이 없는 상태로 정리됨. 반복된 판단 기준은 일관되게 **"구현 부담 최소화"**와 **"SNS 피로감 탈피라는 브랜드 톤 우선"** 두 가지였다.
