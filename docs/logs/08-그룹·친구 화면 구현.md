# 그룹·친구 화면 구현

- 범위: `frontend/src/app/groups/`, `frontend/src/app/friends/`, `frontend/src/lib/api.ts`
- 목표: "도메인 단위로 묶어서 진행" 절충안의 두 번째 배치 — 그룹 CRUD + 친구 관계 화면
- 관련 문서: [일기 화면 구현](./07-일기%20화면%20구현.md)

## 진행 내용

### 그룹 (`/groups`, `/groups/[id]`)
- 목록: `GET /group/mine`, 그룹 생성 폼(`POST /group`), 초대 코드로 참여 폼(`POST /group/join`)
- 상세: `GET /group/:id` — 그룹명, 초대 코드, 멤버 목록(역할 포함), 그룹 나가기(`DELETE /group/:id/leave`)

### 친구 (`/friends`)
- 받은/보낸 요청, 친구 목록을 한 화면에서 관리
- 요청 보내기(`POST /friend/requests`), 수락(`PATCH .../accept`), 거절/취소(`DELETE`), 언프렌드(`DELETE /friend/:friendUserId`)

### 홈 화면에 내비게이션 추가
헤더에 "그룹"/"친구" 링크 추가 (기존엔 일기 목록으로만 진입 가능했음)

## 발견한 버그: `apiFetch`의 빈 응답 처리

`friend`/`group`의 삭제·수락·거절류 엔드포인트는 NestJS 기본 동작상 `204`가 아니라 **빈 바디 `200`**을 반환하는데, 기존 `apiFetch`는 `res.status === 204`일 때만 JSON 파싱을 건너뛰었음 — 빈 바디 200 응답에 `res.json()`을 호출하면 파싱 에러가 남. 배치 1(일기 삭제)에서부터 잠재된 버그였는데 그땐 `confirm()` 다이얼로그 때문에 라이브 테스트를 안 해서 못 잡았고, 이번에 친구 수락/거절 로직을 짜면서 발견해 고침.

```ts
// 고치기 전: 204만 예외 처리 → 빈 바디 200에서 크래시
return res.status === 204 ? null : res.json();
// 고친 후: 실제로 바디가 있는지로 판단
const text = await res.text();
return text ? JSON.parse(text) : null;
```

## 알려진 UX 갭: 친구 검색 기능 없음

기획서(v3)에는 "초대 링크 공유 방식"으로 친구를 추가한다고 되어 있는데, 실제 백엔드는 `addresseeId`(내부 User UUID)를 직접 받는 방식으로만 구현되어 있고 초대 링크/검색 기능은 없음. 이번 배치에서는 임시로 "내 사용자 ID를 공유해서 요청을 받는" 방식(UUID를 직접 복사해서 입력)으로 MVP를 구성함. 제대로 된 초대 링크 시스템은 백로그.

## 검증

- `tsc --noEmit`, `eslint` 클린
- **2개 테스트 계정으로 교차 검증**: 브라우저는 계정을 하나만 유지할 수 있어서(Firebase 세션이 프로필 단위로 공유됨), 같은 탭에서 로그인→작업→로그아웃→다른 계정 로그인을 반복하며 순차 테스트
  - A가 그룹 생성 → 초대 코드 확인 → B가 그 코드로 참여 → 그룹 상세에 A(owner)/B(member) 둘 다 표시되는 것 확인
  - B가 A의 ID로 친구 요청 → A의 "받은 요청"에 B가 뜸 → 수락 → 양쪽 다 "친구 목록"에 반영되는 것까지 확인 (`FriendRequest`/`Friendship` 분리 설계가 프론트까지 맞물려 정상 동작)
- 테스트 중 예전 Postman 테스트로 만들어둔 그룹의 초대 코드(TTL 7일)가 만료되어 400 에러가 난 걸 확인 — 프론트 버그 아니라 백엔드가 의도대로 만료 처리한 것. 새 그룹을 만들어서 재검증함
