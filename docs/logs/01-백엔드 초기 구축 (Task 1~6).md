## Task #1 — schema.prisma 작성

ERD 설계 문서(13개 엔티티)를 `backend/prisma/schema.prisma`로 옮겼다.

- **산출물**: `User`, `NotificationSetting`, `Friend`, `Groups`, `GroupMember`, `Diary`, `DailyPrompt`, `DiaryGroupShare`, `GroupQuestion`, `GroupAnswer`, `QuestionBookmark`, `AnswerBookmark`, `ChatMessage` — 13개 모델
- **부딪힌 문제**: Prisma 7부터 `datasource.url`을 `schema.prisma`에 직접 못 씀(`P1012` 에러) → `prisma.config.ts`가 `DATABASE_URL`을 대신 읽도록 분리된 게 Prisma 7의 새 설정 구조

---

## Task #2 — PostgreSQL 환경 준비 및 .env 설정

로컬 개발용 PostgreSQL을 Docker로 띄웠다.

- **산출물**: 루트 `docker-compose.yml`(`postgres:16` 이미지, `monolog-postgres` 컨테이너, 데이터 영속을 위한 named volume), `backend/.env`의 `DATABASE_URL`
- **진행 방식**: Docker Desktop 설치는 GUI/관리자 권한이 필요해 사용자가 직접 진행, 이후 컨테이너 기동·헬스체크는 자동화

---

## Task #3 — 최초 마이그레이션 생성

`npx prisma migrate dev --name init`으로 `schema.prisma`를 실제 DB 테이블로 변환했다.

- **산출물**: `backend/prisma/migrations/20260813054256_init/migration.sql`
- **핵심 개념**: `migrate dev`는 스키마와 마이그레이션 히스토리(`_prisma_migrations` 테이블)를 diff해서 SQL 파일을 생성·적용·기록하는 방식 — Flyway/Liquibase와 유사하며, JPA의 `ddl-auto: update`와는 다름(자동 스키마 동기화가 아니라 버전 관리되는 변경 이력)

---

## Task #4 — Nest 모듈 스캐폴딩

8개 모듈(`prisma`, `auth`, `user`, `friend`, `group`, `diary`, `qna`, `chat`)의 뼈대를 만들고 DI 그래프에 연결했다.

- **산출물**: `PrismaModule`(`@Global()`, `PrismaService`가 `onModuleInit`/`onModuleDestroy`로 커넥션 관리), `ChatGateway`(REST 대신 WebSocket), 나머지 5개 도메인 모듈은 빈 Controller/Service 껍데기
- **부딪힌 문제 5가지** (전부 "Prisma 7 + NestJS + Windows" 조합에서 비롯):
  1. Prisma 7의 신규 클라이언트 생성기(`"prisma-client"`)가 ESM 전용(`import.meta.url` 사용) → CommonJS와 충돌 → 구버전 `"prisma-client-js"`로 전환
  2. 커스텀 `output` 경로 지정 시 `nest build`의 `dist/src/...` 구조 때문에 상대경로 깊이가 어긋남 → 기본 위치(`node_modules/@prisma/client`)로 되돌려 해결
  3. Prisma 7부터 `PrismaClient`에 드라이버 어댑터(`@prisma/adapter-pg`)가 필수 → `PrismaService` 생성자에서 명시적으로 주입
  4. NestJS는 Spring Boot와 달리 `.env`를 자동 로드하지 않음 → `main.ts`에 `import 'dotenv/config'` 추가
  5. Windows에서 백그라운드 `node.exe` 프로세스가 `kill`로 안 죽는 경우가 있어 `EADDRINUSE` 발생 → `taskkill`로 수동 정리

---

## Task #5 — Firebase Auth Guard 구현

Firebase ID 토큰을 검증하는 인증 가드를 만들고 전역에서 쓸 수 있게 등록했다.

- **산출물**: `FirebaseAdminService`(첫 `verifyIdToken()` 호출 시점에 지연 초기화 — Firebase 프로젝트 자격증명이 없어도 앱은 정상 부팅), `FirebaseAuthGuard`(`Authorization: Bearer <token>` 검증 후 `request.user`에 디코딩 결과 저장), `AuthModule`을 `@Global()`로 등록해 모든 모듈에서 import 없이 사용 가능
- **부딪힌 문제**:
  - `firebase-admin` v14부터 구버전 네임스페이스 API(`admin.auth()`, `admin.credential.cert()`)가 완전히 제거되고 `firebase-admin/app`, `firebase-admin/auth` 서브패스 import로 바뀜
  - `firebase-admin`의 내부 의존성(`jwks-rsa` → `jose`)이 ESM 전용 빌드라 **Jest에서만** 파싱 에러 발생 — 실제 Node 런타임(`node dist/src/main.js`)은 `require(esm)` 상호운용으로 문제없이 로드됨을 직접 확인. 테스트는 `FirebaseAdminService`를 모킹해 격리

---

## Task #6 — user 모듈 엔드투엔드 구현 (첫 세로 슬라이스)

`user` 모듈을 Controller → Service → Prisma까지 실제로 동작하게 채워, `FirebaseAuthGuard`로 보호되는 첫 API를 완성했다.

- **산출물**:
  - `POST /user` — 최초 로그인 시 프로필 등록/동기화 (firebaseUid 기준 upsert)
  - `GET /user/me` — 내 전체 프로필 조회
  - `GET /user/:id` — 타인의 공개 필드만 조회 (`email`, `firebaseUid`는 응답에서 제외)
  - `@CurrentUser()` 커스텀 파라미터 데코레이터 — 가드가 채운 `request.user`를 컨트롤러에서 꺼내는 재사용 가능한 헬퍼
  - 전역 `ValidationPipe` 등록 (`class-validator` DTO 검증 활성화)
  - `src/auth/firebase/__mocks__/firebase-admin.service.ts` — Jest manual mock, 앞으로 `FirebaseAuthGuard`를 쓰는 모든 컨트롤러 테스트에서 재사용
- **부딪힌 문제**:
  - `@CurrentUser() firebaseUser: DecodedIdToken`처럼 데코레이터 파라미터에 인터페이스 타입을 쓰면, `emitDecoratorMetadata`가 런타임 참조를 만들려다 실패 → `import type`으로 명시해 해결
  - Task #5의 Jest/jose ESM 충돌이 `@UseGuards(FirebaseAuthGuard)`를 쓰는 모든 컨트롤러 테스트에서 재발할 것으로 예상 → 매번 인라인 모킹 대신 재사용 가능한 manual mock으로 한 번에 해결
- **검증**: 빌드/린트/테스트(15 스위트, 25 테스트) 전부 통과 + 실제 부팅 후 curl로 스모크 테스트 — 토큰 없음/잘못된 토큰 모두 401로 안전하게 차단, 라우트 3개 정상 매핑 확인
- **남은 제약**: 실제 Firebase 프로젝트가 없어 "진짜 토큰으로 정상 통과"까지는 검증하지 못함 — `.env`의 `FIREBASE_*` 값을 채워야 최종 확인 가능

## 이번 6개 Task를 관통하는 공통 주제

1. **Prisma 7의 변화**: `datasource.url` 분리, 드라이버 어댑터 필수화, ESM 전용 신규 생성기 — 대부분의 예상치 못한 문제가 여기서 비롯됨
2. **CJS/ESM 경계 문제의 반복 등장**: Task #4(Prisma 생성기), Task #5·#6(firebase-admin의 `jose` 의존성)에서 같은 근본 원인(생태계가 점점 ESM으로 이동 중)이 다른 모습으로 계속 나타남 — 실제 런타임은 `require(esm)`으로 대부분 문제없지만 Jest는 별도 대응이 필요
3. **NestJS ≠ Spring Boot인 지점들**: `.env` 자동 로드 없음, 명시적 모듈 임포트 원칙(`@Global()`로 예외 처리), 데코레이터 메타데이터 기반 DI — Spring/JPA 경험을 기준으로 계속 대조하며 이해한 부분들
